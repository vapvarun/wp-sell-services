## Contracts locked (and why)

The Pro plugin is a **hard consumer** of this plugin, so the public surface is
frozen for the entire cycle. `migrations:` is intentionally empty — a hardening
release must not move any externally-observable symbol. The contract block was
seeded from `audit/manifest.json` and then cross-checked against what the Pro
source actually consumes:

- **41 `wpss_*` hooks** that Pro registers callbacks on (`add_action` /
  `add_filter`), verified by grepping `../wp-sell-services-pro`. The most
  load-bearing: `wpss_loaded` (Pro's entry point), `wpss_ecommerce_adapters`,
  `wpss_payment_gateways`, `wpss_storage_providers`, `wpss_wallet_providers`,
  `wpss_dashboard_sections` + `wpss_dashboard_section_template`,
  `wpss_api_controllers`, `wpss_settings_tabs`, `wpss_gateway_cards`,
  `wpss_order_status_changed`, `wpss_service_meta_fields` and the
  `wpss_service_max_*` limit filters. Renaming or dropping any of these silently
  breaks a Pro feature with no static error.
- **15 free service/model classes Pro instantiates or extends directly** —
  `Integrations\Contracts\*` (37 refs), `Models\ServiceOrder` (15),
  `API\RestController` (11, Pro controllers extend it), `Services\Scheduler` (8),
  `Models\Service`, `Services\{ServiceManager, OrderService, EarningsService,
  TippingService, MilestoneService, CommissionService}`, `Models\VendorProfile`,
  etc. Their **method signatures are part of the contract** even though the
  schema only models hooks/routes/options/etc. This is called out here because
  the input-handling refactor (Wave 2) touches files that may call into these
  services — implementers must not change a shared signature to make a refactor
  cleaner. Flagged as a needs-owner-decision item below.
- **138 REST endpoints / `wpss/v1`** — the namespace and the 24 controller
  bases are locked. The route list in the manifest is the controller-base set
  (full per-route enumeration is deferred in the manifest itself); the verifier
  diffs the live route table, so any renamed/removed route halts.
- **19 shortcodes, 6 blocks, 18 tables, 4 CLI commands, 21 option keys** — all
  frozen. Blocks are tracked via the live block registry by the verifier.

## Stability annotations

- **Wave 1 (security)** is pure backend PHP — lowest blast radius, runs first so
  the contract verifier validates against a clean security base. The two
  directions are file-disjoint (`Admin/*` vs `Frontend/AjaxHandlers.php`) so they
  parallelize safely. Risk: adding a `current_user_can` after a nonce can change
  a 200 into a 403 for a path that was previously (incorrectly) open — the
  `admin-moderation-actions` + `pro-pair-still-loads` journeys exist to catch a
  guard that is too tight or that blocks a legitimate Pro-driven action.
- **Wave 2 (input handling)** — refactoring `$_POST`/`$_GET` iteration to
  explicit-key reads is the highest-correctness-risk change: an iteration loop
  may currently absorb dynamically-named fields (e.g. repeatable package rows).
  Explicit-key reads must preserve the full set of keys, hence the
  `admin-metabox-save` journey verifying packages/addons persist. `AjaxHandlers.php`
  appears in both Wave 1.2 and Wave 2.2 — they are in **different waves**, so
  they never run in parallel and never collide; serialization is the depends_on
  edge `wave-2 -> wave-1`.
- **Wave 3 (frontend UX)** — JS/CSS only, zero PHP, zero contract surface. Must
  reuse the **existing** `assets/js/admin-toast.js` and
  `assets/js/components/wpss-ux-primitives.js` rather than add a new dependency
  (the `ux-audit` gate enforces no native alert/confirm and design-token
  compliance). The CSS direction regenerates `.min` files via `npm run build`;
  do not hand-edit minified output.
- Performance/N+1/caching/pagination are **not** in scope — this is hardening of
  named findings, not a perf pass. No directions carry `wp-performance`.

## Why the waves are ordered this way

Mapped onto the 9-phase ordering, all the work lives in the **security ->
admin-ui/frontend** band (there is no data-layer or REST change). Within that
band priority drives the order: security findings first (journey `fix`,
priority 3), then input-handling refactors (journey `improve`, priority 2 but
sequenced after security by an explicit depends_on because they share
`AjaxHandlers.php` across waves), then JS/CSS UX cleanup, then the read-only
audit verdict last. Each non-final wave runs `qa-suite` + `browser-smoke` plus
the builtin `contract` gate so a Pro-breaking change halts immediately.

## Needs owner decision

1. **AjaxHandlers nonce triage (Wave 1.2).** The baseline says ~13 findings are
   *likely* object-ownership false positives but some "may be real gaps." The
   planner cannot decide per-handler which is which. The direction is scoped to
   *triage + document accepted patterns, add a guard only where ownership truly
   isn't checked*. If the implementer finds a real gap that needs a shared
   ownership helper, that is a contract-adjacent change — escalate, don't invent.
2. **Shared service-signature freeze vs. refactor cleanliness (Wave 2).** If an
   explicit-key refactor would be cleaner by changing a method signature on a
   Pro-consumed service/model, that is **not allowed** under this plan — confirm
   the owner is fine keeping the signature and doing the refactor locally, or
   sanction the signature change with a `migrations:` entry first.
3. **CSS scope guess.** The CSS direction (3.2) targets `dashboard.css`,
   `wizard.css`, `admin.css` by inference from the baseline ("dashboard/wizard
   CSS"). Confirm these are the right source files (vs. SCSS sources) before the
   run so the implementer edits sources, not build artefacts.
4. **site_url / local_wp_site** in the manifest are best-guess
   (`wpsellservices.local`). Correct them if the Local site slug differs, or the
   functional gates can't reach the live site.
