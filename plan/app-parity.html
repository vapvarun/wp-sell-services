    What the plugin still owes 6 open · all carded

    F-2 and F-6 should not wait. One blocks App Store submission outright; the other is a live authorisation hole on the current release. All six now sit in Basecamp Ready for Development in the order below — the plugin work is being wrapped before app screens start.

    F-2

    No report and no block route exists anywhere in Free or Pro

    Zero route matches across both plugins. App Store Guideline 1.2 requires both wherever members post content to each other — which here is every order conversation, review and proposal. This blocks submission and the app cannot work around it.

    ◆ zero matches for a report/block/flag route in src/ of both plugins

    F-6

    A suspended vendor is blocked on the web and not in the API

    ServiceWizard.php:276 blocks suspended and pending vendors before the web form renders. ServicesController::create_item_permissions_check() does not — it calls check_permissions(), which is login plus rate limit only, then a filter. Neither consults wpss_get_vendor_status(). A suspended vendor holding a valid Application Password can publish services through the API. EarningsController:674 does check status, so the gate is understood — just not applied on the write paths.

    ◆ src/API/ServicesController.php:989 · src/API/RestController.php:60 · src/Frontend/ServiceWizard.php:276

    F-1

    OrdersController duplicates the status label map, incompletely and unfilterably

    get_status_label() carries a private map of 11 statuses and falls through to ucfirst($status) for the rest. Seven fall through — including pending_payment, pending_requirements and pending_approval, the three most common buyer-facing states — so the API answers "Pending_payment", underscore and all.

    Meanwhile wpss_get_order_statuses() already has all 18, already translated, already filterable via wpss_order_statuses. The REST layer just does not call it. The app compensates with its own English map, so statuses render in English on every localised site and no owner's filter ever reaches the app.

    ◆ src/API/OrdersController.php:1691-1707 vs src/functions.php:2576,2588

    F-3

    Two withdrawal rails, no declared winner

    Free ships /withdrawals; Pro ships /wallet/withdraw and /wallet/balance. Both are live simultaneously on a Pro site and nothing in /settings says which one a client should use. The app picked Free's and may be showing a seller a balance Pro considers secondary.

    ◆ live index · WalletController.php (Pro) vs EarningsController.php (Free)

    F-4

    The app contract publishes only 3 feature flags

    buyer_requests, disputes, realtime. Milestones, tips, extensions, portfolio and seller levels each have a real on/off or licence state and none is published — so a client cannot tell disabled from not built, and the three biggest missing features cannot be gated safely when they ship.

    ◆ src/API/API.php:697-704

    F-5

    Order statuses are not published in /settings

    The app must carry its own copy of an 18-value vocabulary that any site can edit through wpss_order_statuses. This is the exact shape of the Listora "Expired" filter bug and the Career Board pipeline-stage bug: a client-side copy of a server-owned list that scores ✅ while drifting. Publishing { slug, label } closes the whole class.

    ◆ GET /settings carries no status list · pairs with F-1

    What ships today read in code, not inferred from commits

    The app is a competent buyer client and a thin seller one. Everything below was re-read at the call site on 2026-08-08.

    • Discovery — services, categories, search
    • Service detail — packages, FAQs, reviews, summary
    • Seller profile — services and portfolio, read-only
    • Favourites — whole group covered
    • Cart — whole group covered
    • Checkout hand-off — one path on both rails; the server prices and clears the cart
    • Orders — list, detail, and all 10 lifecycle verbs
    • Requirements — submit and skip
    • Deliverables — avoids the status-only /deliver trap
    • Review an order
    • Messaging — conversations, unread counts
    • Notifications — read, read-all, badge
    • Buyer requests — browse, post, mine
    • Proposals — send, list, withdraw
    • Earnings and withdrawal — the whole Free rail
    • Vacation mode
    • Auth — all 8 routes
    • Licence gate — fails closed on app_enabled, open on min_app_version

    Not verified — do not read absence as assurance

    • Runtime behaviour. No simulator run. Every row on this page is code-level; nothing has been seen working.
    • The ban gate. Read in code and found open (F-6) — not yet proven against a live suspended vendor holding an Application Password.
    • The licence gate on a device. The logic in utils/gate.ts is correct; it has not been watched blocking a connect.
    • A live API flow run. Listora's equivalent run found 3 of 22 rows scored wrong from commit messages. This product has not had that check.
    • The previous coverage number was wrong. The first matrix claimed 94 of 178 routes called by grepping any string starting with a slash. Resolving real call sites gives 58 of 179.
