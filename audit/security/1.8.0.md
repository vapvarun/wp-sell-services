### The new interpolated-SQL lines, each read

Every one interpolates a table name built from `$wpdb->prefix` or a class
constant, or a list of ids passed through `intval`. None carries request data.

- Admin attention counts (vendor profiles, disputes, withdrawals): table names only.
- Orders list total: `$from` and `$where` are built in the table class, values go through `prepare()`.
- `UtcMigration::plan()`: `SELECT MAX(id) FROM {table}`, table from a class constant.
- Vendor verification tiers read: table name only.
- `wpss_delete_demo_content()`: service ids from `get_posts()`, each `intval`.
- CLI test-flow cleanup: ids from the command's own fixtures, admin/CLI only.

## G3 - Reviewed diff (`v1.7.2..HEAD`, src and templates, both plugins)

Independent review of the diff, then each finding verified in the code.

### HIGH - fixed: a buyer could be refunded for a payment that had already paid an order

**Who and what:** any buyer, using only their own payment id. Re-sending the
confirm call for a settled payment with a request that fails (a service that
does not exist, an order now paid, a cart since changed) reached the
"charge could not become an order, refund it" branch, which never asked
whether that charge had already paid an order.

**Where:** Stripe `refund_unsettled_charge()` (AJAX and REST confirm), PayPal
`capture_and_settle()` (two branches), Pro Razorpay
`settle_verified_payment()` (two branches). The Stripe and Razorpay branches
predate 1.8.0; the PayPal one became reachable in 1.8.0.

**Fix:** one shared guard, `CheckoutIntentService::refund_unsettled()`, that
every one of those branches now calls. Under the same per-transaction lock as
settling: a charge that already paid an order is not refunded; a charge given
back is remembered and cannot settle an order afterwards. `settle()` also
answers with the existing order before it compares amounts.
Test: `tests/test-refund-unsettled-guard.php`.

### LOW - accepted: the Test gateway marks orders paid on a site in demo mode

`TestGateway` is offered only on the standalone rail with no live gateway
configured and the owner not opted out, with an admin notice. Intended for
evaluation; payouts on such a site are manual. Not changed.

### LOW - accepted, carded: request-context uploads accept the full private file list

A signed-in member can upload a zip or pdf with `context=request` without then
attaching it to a request. Avatar, profile, service and portfolio uploads are
capped to images; this context is not. Follow-up card filed.

### Known, tracked for the next version

The `wpss_request` post type uses WordPress's generic post capabilities, so a
member holding an editing role can alter a proposed-on request through core
routes. Default roles cannot. Card filed (own capability type).

## Scanner-visible but safe

- `wp_ajax_nopriv_*` (7): see 1.7.2 triage.
- Interpolated SQL: table names and `intval` id lists only, listed above.
- `readfile-serve` (`src/functions/files.php`): the served path is the private order-files directory, the order id, and `basename()` of the stored file name, so a stored name cannot climb out of that order's folder. Unchanged since 1.7.2.
- `esc-sql-on-nonscalar`: pre-existing, on a scalar in practice; carded in 1.7.2 and not re-read for this release.

## Checked and safe in this diff

New admin handlers (`wpss_admin_search`, `wpss_manual_order_quote`, refund
retry, vendor role cleanup) check `manage_options` and a nonce. Withdrawal
cancel is scoped to the vendor's own pending request. Reports: create needs
login and refuses own content; list and resolve are admin-only. Webhooks settle
through `settle_webhook_order()` with amount, currency and ownership checks.
New templates escape their output. `[wpss_login]` redirects pass
`wp_validate_redirect()`.

Not reviewed in depth: `UtcMigration` and CLI commands (admin/CLI only), the Pro
analytics collectors.

## Plugin Check on the built zips (clean Docker install, WP 7.1.1)

Errors in the plugins' own code, 1.8.0 against the published 1.7.2 zips, same
stack and same command:

| Plugin | 1.8.0 | 1.7.2 | Delta |
|---|---:|---:|---:|
| Free | 424 | 424 | 0 |
| Pro | 17 | 14 | +3 |

By type, Free: `PreparedSQL.NotPrepared` +32, `I18n.MissingTranslatorsComment`
-30, `DirectDB.UnescapedDBParameter` -2. Pro: `PreparedSQL.NotPrepared` +5,
`DirectDB.UnescapedDBParameter` -2.

The `NotPrepared` reports are token-level: the sniff names things like
`prepare`, `$this`, `$user_id` and class constants inside calls that are
already prepared or that interpolate a table name. None names a request
superglobal. The standing backlog is a card, not a release blocker; the one
tolerated intentional error is `plugin_updater_detected` (bundled EDD updater).
