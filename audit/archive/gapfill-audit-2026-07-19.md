# WP Sell Services — Gap-fill Audit (disputes, admin, discovery) — 2026-07-19

## Executive summary

Static source audit of three WP Sell Services clusters — the buyer/vendor dispute flow, the admin screens, and the discovery/single-service blocks — surfaced **11 confirmed defects (2 P1, 8 P2, 1 P3) plus 3 unverified P3 leads**. Two themes dominate and both hurt the core marketplace loop:

1. **Disputes have no on-site surface at all.** The dispute view and list templates are orphaned — a buyer/vendor can *open* a dispute (the button, AJAX handler, and REST API all work) but has nowhere on the website to read the other party's response, add evidence, or see the resolution. Only the mobile/REST client can use disputes. Behind that wall sit three latent template/data-contract bugs (evidence lost to `absint()`, array-as-object reads, wrong initiator column) that will bite the moment the P1 wiring lands.
2. **Top-of-funnel discovery blocks silently do nothing.** The standalone Service Search and Service Categories blocks submit `wpss_search`/`wpss_category`, but the archive only reads `search`/`category` — every keyword and category filter is dropped. Featured Services hides every never-reviewed listing (the exact ones owners feature). Guest add-to-cart dead-ends with a 5-second-fading error and no login link. The Seller Card "View Profile" CTA points at the core author blog archive, not the vendor storefront.

The admin cluster is healthier: three real defects (one big-site scalability risk on the hidden Manual Order page; two bulk-action flows that discard their own per-row failure reports on `location.reload()`), all P2, all admin-only.

Findings are from **static source tracing only — no live WordPress, browser, or seeded dataset**. All "what the user sees" statements for latent template bugs are reasoned from the data contract, not observed at runtime (called out per-item below).

## Secondary / unverified

- **P3 (CONFIRMED, latent)** — `templates/disputes/dispute-view.php:240`: evidence is stored/returned as associative arrays but the template reads every field as an object (`$item->created_at`, `->user_id`, `->type`, `->content`, `->description`). Under PHP 8 each `->` on an array returns `null` + a warning, so evidence renders blank. Only manifests once the orphaned template is wired (the repo's own `journey-audit-2026-07-19.md` notes it is un-wired). Fix: use array syntax or cast rows to objects in the loader — consistently with `DisputeService`.
- **P3 (unverified)** — `templates/disputes/dispute-view.php:54`: header reads `$dispute->initiator_id`, but `DisputeService::get()` returns the raw row whose column is `initiated_by`, so "Opened by …" always shows "Unknown". Only `Models\Dispute::from_db()` maps the column, and that model doesn't feed the template. Fix: read `$dispute->initiated_by` or standardize the template's data on `Models\Dispute`.
- **P3 (unverified)** — `src/Admin/Pages/ServiceModerationPage.php:572`: approve/reject/bulk use native `confirm()`/`prompt()` while the rest of the admin uses modal + toast (`wpssConfirm`/`wpssToast`); `window.prompt` is disabled by some browsers/enterprise policies and unusable on mobile admin, so reject-with-reason can become unreachable. Also `cb-select-all-1/2` checkboxes lack `aria-label` (unlike Withdrawals/Vendors). Fix: swap to `wpssConfirm` + a reason field; add the aria-labels.
- **P3 (unverified)** — `src/Admin/Pages/SetupWizardPage.php:928`: the wizard "Save & Continue" handler calls `goToStep(step+1)` unconditionally and never checks `response.success`; `.fail()` only fires on transport errors, not on `wp_send_json_error()` (HTTP 200 `{success:false}`), so a failed step save silently advances and loses that step's config. The file's own page-create/demo-import handlers *do* gate on `response.success`. Fix: only advance on success, else show `wpssAdminNotice(response.data.message)` and stay on the step.

## Coverage (per cluster, honest)

**Disputes / templates flow** — Full buyer/vendor dispute journey traced in the free repo: both templates confirmed orphaned (grep of all `src/` for `wpss_get_template`/`wc_get_template`/`include` returns only self-references), no `disputes` dashboard section, no WC endpoint (`Plugin.php:490` deliberately avoids `add_rewrite_endpoint`), no dispute shortcode. Open/evidence/schema paths and the admin `render_dispute_detail` all read. **Not done:** no live WordPress or browser, so findings 4/5/6 are latent and reasoned, not observed at runtime. **Did not open `wp-sell-services-pro`** — Pro could wire a disputes section via the `wpss_dashboard_sections` / `wpss_dashboard_section_template` filters (both exist), which would mask the P1 on Pro sites; free-only installs (the majority) still have no on-site dispute surface. Did not fully audit the admin resolution POST handler or the REST `DisputesController` response mapping (an admin-side resolution defect or a mobile evidence-content mismatch could exist beyond what's reported); did not deep-audit `DisputeWorkflowManager` escalation/timeline.

**Admin screens usability** — Fully traced ManualOrder (render + create), Notifications, AuditLog, ReviewModeration, ServiceModeration, Withdrawals (bulk + modal), Vendors (bulk paths), and SetupWizard (render + handlers + JS); confirmed the shared `wpssToast`/`is_plugin_page` enqueue so toast paths resolve. **Not done:** did not audit `Settings.php` (3067 lines) or `admin-settings*.js`, `UpgradePage.php`, or the Vendors single-vendor detail-modal sub-tabs (commission/vacation/level/portfolio AJAX ~960-1670) beyond confirming they gate on `response.success` — those could hold further save→apply or a11y gaps. Logic verified by reading source only; the ManualOrder scalability impact is reasoned from the unbounded queries, not measured against a seeded large dataset.

**Discovery / single-service blocks** — Buyer funnel traced end-to-end: the five discovery blocks cross-checked against `ServiceArchiveView::modify_archive_query()` (reads canonical `search`/`category`/price/rating/delivery/sort), single-service PHP+JS through `openOrderModal → addToCart → wpss_add_service_to_cart`, cart shortcode/template, and all writers of `_wpss_starting_price`/`_wpss_rating_average`/`_wpss_review_count`. **Not done:** no live WP, so no visual verification across generic/premium themes or ≤480px, and the FeaturedServices INNER-JOIN exclusion is inferred from documented `WP_Query` `meta_key` ordering semantics + the confirmed absence of a `_wpss_rating_average` initializer (not confirmed against a seeded zero-review dataset). Did not audit BuyerRequests block internals, reviews/faqs partials, or the WooCommerce/EDD checkout-adapter handoff beyond the add-to-cart handler. One non-finding: a nested `<button>` inside the card's `<a>` (`content-service-card.php:111`) is invalid HTML but functionally neutralized by `frontend.js` `stopPropagation`, so it was not raised.
