# 1.5.1 — Full-surface audit and consolidation plan

**Scope:** `wp-sell-services` (Free) + `wp-sell-services-pro` (Pro), branch `1.5.1`.
**Status:** planned, not started. Decisions taken (see §2). No product code written yet.
**Method:** every claim below was reproduced at runtime on `wss.local` (Free 1.5.1 / Pro 1.5.1) or verified by reading the code. Claims that did not survive verification are recorded in §7 so they are not re-raised.

---

## 1. Root causes

Not a list of bugs. Four systemic causes, plus four discrete items. Every fatal reproduced traces to one of these.

### R1 — Hydration boundary

The 25 non-strict files in Free `src/` are almost exactly the data layer: every repository, `DisputeService`, `ProposalService`, `BuyerRequestService`, `SchemaManager`, `MigrationManager`. They return raw `stdClass` rows from `$wpdb`, where **every column is a string** (`total` is `decimal(11,3)` → `"75.000"`; `id` → `"12"`).

Consumers are strict. Free `src/` is 168/193 strict; **Pro `src/` is 119/119 strict**, so every Pro consumer of a Free repository sits on the dangerous side.

Proven at runtime from a `declare(strict_types=1)` caller:

```
raw row types: id=string  total=string
FATAL wpss_get_order_url(): Argument #1 ($order_id) must be of type int, string given
FATAL wpss_format_price(): Argument #1 ($price) must be of type float, string given
```

`int` params are exactly as dangerous as `float`. Most affected call sites take `int`.

**Not bugs (verified, do not "fix"):** all `templates/*.php` are non-strict, so coercive mode applies — the *calling* file governs. Hook callbacks are invoked from non-strict `class-wp-hook.php`, so typed closures in `Plugin.php` are coerced. Typed model properties (`public float $total`) are safe.

### R2 — `OrderProviderInterface` omits its own write contract

`src/Integrations/Contracts/OrderProviderInterface.php` declares 10 read methods and **none** of `create_order()`, `create_orders_from_cart()`, `mark_as_paid()` — yet 8 files call them on the interface.

| Provider | create_order | create_orders_from_cart | mark_as_paid |
|---|---|---|---|
| `StandaloneOrderProvider` | yes | yes | yes |
| `WCOrderProvider` | **no** | **no** | **no** |
| `EDDOrderProvider` | **no** | **no** | **no** |
| `SureCartOrderProvider` | yes (incompatible signature) | **no** | **no** |
| `FluentCartOrderProvider` | yes (incompatible signature) | **no** | **no** |

Accounts for **38 of 43** `method.notFound` errors across both baselines.

**Severity: highest.** Unauthenticated external POST → fatal, on the paying-customer configuration:

1. Pro registers adapters only when licensed (`wp-sell-services-pro.php:205-213` — `if ( ! $is_licensed ) { …; return; }` sits immediately before `add_filter( 'wpss_ecommerce_adapters', … )`).
2. `WooCommerceAdapter::is_active()` is just `class_exists( 'WooCommerce' )`, and `IntegrationManager::detect_active_adapter()` **prefers non-standalone**. So on a licensed Woo site `wpss_get_order_provider()` returns `WCOrderProvider`.
3. Free's gateways stay hooked on **every** rail, deliberately — `Plugin.php:1895`:
   > *"Gateways stay REGISTERED on every rail, deliberately… init() is also what hooks each gateway's webhook handler… a later refund, dispute or delayed-capture webhook for one of those still has to be received and applied."*
4. Those handlers resolve the provider at runtime and call `mark_as_paid()`: `PayPalGateway.php:664, 949, 980, 1040, 1092`; `StripeGateway.php:1348`.

So the exact scenario the comment exists to protect hits `Call to undefined method WCOrderProvider::mark_as_paid()`. Gateways null-check the provider (`'No order provider.'`) but never check the method exists. Pro's `RazorpayGateway.php:658, 801, 871` do not even null-check.

**Why this survived QA:** it needs licence + WooCommerce + a legacy gateway order. An unlicensed sandbox registers no Pro adapter at all, so Standalone always wins and the path is unreachable. Confirmed locally — could not trigger it without a licence.

**Key enabler for the fix:** all providers already share one canonical store. `WCOrderProvider::get_order()` returns `ServiceOrder::find( $order_id )`; `StandaloneOrderProvider::mark_as_paid()` writes `{$wpdb->prefix}wpss_orders`. The write methods operate on the **marketplace order record**, not on rail-specific objects — so one shared implementation is correct for all five providers.

**PHPStan under-reports this class.** `CheckoutIntentService.php:270, 292, 302, 328, 349` calls the same three methods with **zero** baseline entries, because `$provider` is an untyped `@param object`. Reached from `StripeGateway.php:1068,1130` and `PayPalGateway.php:718`. A fix that only chases baseline entries misses these five.

### R3 — Render duplication

19 shortcodes, 6 blocks, and **no shared renderer between them**. The service grid exists three times.

`wpss_render_services_grid()` (`functions.php:5421`) is already the canonical renderer — paginated, template-backed via `content-service-card.php`, fires `wpss_service_card_*` hooks, renders the favorites toggle. **Neither `[wpss_services]` nor `wpss/service-grid` calls it**; only REST `GET /services/grid` and one AJAX handler do.

All 4 shortcode fatals live in the un-shared copy. All 6 blocks render clean.

Templates that already exist, are theme-overridable, and are used by **neither** surface: `templates/content-request-card.php`, `templates/partials/vendor-card.php`. Consolidation is mostly deleting duplicates, not writing new abstractions.

Behavioural divergence, not just markup drift:
- Categories: shortcode links to the **taxonomy archive**; block links to the **CPT archive with the filter param** that `ServiceArchiveView::modify_archive_query` actually reads. The block is correct.
- Buyer requests: block does a raw `WP_Query` with **no expiry filter**, so it shows expired requests the shortcode correctly hides via `BuyerRequestService::get_open()`.
- Request cards read different meta and use different money formatters (`wpss_format_price` vs `wpss_format_currency`).
- Search: two incompatible class vocabularies, so CSS must carry both; block loses the shortcode's `action` override.

## 2. Decisions taken

| Decision | Choice | Note |
|---|---|---|
| R2 fix | ~~Complete the interface + implement in all 4 Pro providers~~ **SUPERSEDED — see §2.1** | Satisfying the write contract would harden the wrong abstraction |

### 2.2 Amendment — deleting `OrderMetabox` must re-home `wpss_admin_order_actions`

Browser-verified 2026-08-10. `wpss_admin_order_actions` is fired from **exactly one place — `OrderMetabox.php:855`** — inside the metabox registered against the non-existent post type. Its only consumer is `OfflineGateway::render_admin_order_actions()` (`OfflineGateway.php:119`).

Consequences, both confirmed in the browser:

1. **The "Mark as Paid" button never renders on any screen.** Loading `admin.php?page=wpss-orders&action=view&order_id=N` for a `payment_method='offline'` + `status='pending_payment'` order produces no button (`.wpss-mark-paid-btn` matches nothing). **An admin cannot confirm an offline payment anywhere in the product** — offline payments can be taken but never marked paid. This is a dead *feature*, not merely dead code, and `wp_ajax_wpss_admin_mark_order_paid` has no UI able to generate its nonce.
2. **Deleting the metabox without re-homing the hook would make this permanent** and remove an extension point Pro or third parties may rely on.

**Required with the deletion:** fire `wpss_admin_order_actions` from `Admin::render_order_detail()` and move the mark-paid UI there, then re-verify the button renders and completes. Filed as its own Basecamp card.

### 2.1 Architectural direction — third parties are payment processors only

> *"Any 3rd party plugin integration is just a payment processor for us. We add services to cart and get them checked out using Woo, SureCart or FluentCart; based on the linked order status we update the order at our end and follow the same trail."*

**The marketplace owns the catalog, the cart, the order and the whole post-payment lifecycle. Third-party plugins are payment processors — like Stripe.**

Flow: services go into **our** cart → payment is handed to the processor → the processor's order status maps back to **our** order status → our trail continues (requirements → delivery → completion → payout).

**The schema already implements this.** `wpss_orders` carries `platform`, `platform_order_id`, `platform_item_id`, `payment_method`, `payment_status`, `transaction_id`. Live data holds `standalone`, `woocommerce`, `request`. `OrderRepository::get_by_external_order( int $platform_order_id, string $platform )` is the link lookup. Status maps already exist at `FluentCartAdapter.php:203` and `WCOrderProvider.php:843`. Decisively, `WCOrderProvider::get_customer_orders()` runs `SELECT * FROM wpss_orders WHERE customer_id = %d AND platform = 'woocommerce'` and hydrates via `ServiceOrder::from_db()` — **it is a filtered view of the marketplace table, not a separate store. Woo never owned orders.**

**This is the documented direction, not a new one.** `CLAUDE.md` 1.3.1 already records "one payment owner" plus the `wpss_pay_order_url` seam, and names the stall: *"EDD/FluentCart/SureCart have no pay-order rail and fall back to the standalone `?pay_order=N` dead end. Known gap, documented."*

**What contradicts the model is `EcommerceAdapterInterface`**, which claims the third party owns four roles: `get_order_provider()`, `get_product_provider()`, `get_checkout_provider()`, `get_account_provider()`. That one wrong abstraction causes R2's fatal (the provider swings globally by active adapter), duplicates checkout (`WCCheckoutProvider` pushes services into the *WooCommerce* cart — the inverse of the intended flow), and lets the post-payment trail diverge per rail.

**The target already exists in two places:** `RazorpayGateway implements PaymentGatewayInterface`, and `WCPayOrderResolver` (264 lines, shipped 1.4.0) is already Woo-as-processor — it hooks `wpss_pay_order_url`, calls `wc_create_order()` purely to collect money, returns `get_checkout_payment_url()`, and remembers the mapping.

**Revised R2 — delete the need for the write contract rather than satisfy it:**

1. **One order authority.** `wpss_get_order_provider()` always returns the marketplace provider, so the 3 write methods only ever land on the single class that implements them. **38 of 43 `method.notFound` errors vanish** instead of being satisfied. No interface change, no 4 implementations.
2. **Resolve the processor per-order.** Webhooks load the order, read `platform`, dispatch to that processor. This is what the `Plugin.php:1895` comment was reaching for — a legacy Stripe order stays handled by Stripe after the site moves to Woo.
3. **Third parties implement `PaymentGatewayInterface`.** Generalize the `wpss_pay_order_url` seam from milestone/tip/extension to *all* payments, and give EDD/FluentCart/SureCart the pay-order rail they lack today (closes the documented 1.3.1 gap).
4. **Retire the order + checkout provider roles.** Product/account roles are a separate call — a Woo store may still legitimately want My Account tabs.
5. Delete "prefer non-standalone" from `IntegrationManager::detect_active_adapter()` for the order role.

**Sequencing — WooCommerce only in 1.5.1 (3,517 lines). EDD / SureCart / FluentCart flow checks move to 1.6.0** (2,483 / 2,328 / 2,113). Everything else in this plan (Phases 0, 1, 3, 4, 5, 6) stays in 1.5.1.

Those three remain **adapters** for 1.5.1 and must keep working unchanged — do not half-migrate them. Only Woo is wrapped as a processor now. This also matches what the sandbox can prove: WooCommerce is installed and licence-enabled here; the other three are not installed at all.

**Hard prerequisite:** a licensed sandbox with WooCommerce (and ideally EDD / SureCart / FluentCart) plus at least one legacy gateway order. Pro registers its adapters **only when licensed** (`wp-sell-services-pro.php:205-213`), so on an unlicensed site no adapter loads, `wpss_get_order_provider()` always returns Standalone, and **none of this work — bug or fix — is reachable or testable.** That is precisely why this class of defect reaches customers rather than QA. Without that environment, Phase 2 can be written but cannot be signed off.

### Phase 2 — third parties become payment processors (R2)

Per §2.1. **1.5.1 ships 2a only. 2c/2d/2e move to 1.6.0** (owner decision, 2026-08-10).

**Why the split.** A payment gateway only has meaning inside *our* checkout, and on a cart rail that checkout does not exist: `wpss_uses_standalone_payments()` is false whenever a non-standalone adapter is active, which gates `PaymentController` route registration in Free (`:55`) and Pro (`:50`), the gateway settings UI (`Settings.php:1739`), and — because `StandaloneAdapter` is not active — the registration of `[wpss_checkout]` and `[wpss_account]` themselves (verified: `/account/` 404s on the Woo rail and the registered-shortcode count drops).

So building `WooCommerceGateway implements PaymentGatewayInterface` now produces a gateway **nothing can select** — dead code, the exact category this release is removing. 2c only becomes reachable once our cart/checkout owns the flow, i.e. together with 2e. They are one change, not two, and they invert a purchase flow that currently works (verified end to end on WC 445 and WC 451).

1.6.0 therefore carries 2c + 2e together, with the EDD / SureCart / FluentCart processors alongside, since all four need the same seam. Two questions to settle before that work starts: does `[wpss_checkout]` become the checkout on **every** rail, and is "our cart" the existing `[wpss_cart]`?

**2a — one order authority.** `wpss_get_order_provider()` always returns the marketplace provider. Delete "prefer non-standalone" from `IntegrationManager::detect_active_adapter()` for the order role. The 3 write methods now only ever land on the class that implements them — **no interface change, no 4 implementations, 38 of 43 `method.notFound` errors vanish.** Type `CheckoutIntentService::$provider` so the analyser sees the 5 call sites it currently cannot (`:270, 292, 302, 328, 349`). Add null guards at `RazorpayGateway.php:658, 801, 871`.

**2b — per-order processor resolution.** Webhooks load the order, read `platform`, dispatch to that processor instead of the globally-active adapter. Satisfies the intent of the `Plugin.php:1895` comment: a legacy Stripe order stays handled by Stripe after the site moves to Woo.

> **Scope correction (browser-verified 2026-08-10).** R2's live exposure is **narrower than the audit implied**. Completing a WooCommerce order does **not** call `mark_as_paid()` — the `woocommerce_order_status_*` handlers update the marketplace order directly, verified with no fatal (§4.2). The reachable fatal is confined to **legacy standalone-gateway orders** (Stripe / PayPal / Offline) whose webhook fires while the site runs the Woo rail. The admin Offline "Mark as Paid" route is *also* affected in principle but is currently unreachable because its UI never renders (§2.2). This lowers R2's likelihood but not its severity: gateway webhooks are unauthenticated external POSTs and remain live.

**2c — NARROWED (owner decision, 2026-08-10).** Since the cart plugin keeps its own checkout (see 2e), there is no need to register the processors as selectable gateways inside our checkout — that checkout does not run on their rails, which is why building `WooCommerceGateway` would have produced something nothing could select.

What remains is real and customer-facing: **give EDD / FluentCart / SureCart the pay-order rail they lack.** `WCPayOrderResolver` implements `wpss_pay_order_url` for WooCommerce by creating a real WC order and returning its native order-pay URL; on the other three rails every milestone / tip / extension / accepted-proposal pay link falls back to `?pay_order=N` and dead-ends on an empty cart. That gap is documented in `CLAUDE.md` 1.3.1 and is the actual defect behind "third parties are payment processors".

**2d — status sync is one path.** One mapping layer (`platform` status → marketplace status), replacing the per-adapter maps at `FluentCartAdapter.php:203` and `WCOrderProvider.php:843`. After payment, every rail rejoins the same trail: requirements → delivery → completion → payout.

**2e — CANCELLED (owner decision, 2026-08-10).**

I had this backwards. 2e said to retire the checkout provider role because `WCCheckoutProvider` pushes services into the *WooCommerce* cart, which I read as "the inverse of the intended flow". It is not. **When a cart plugin is active, it owns the cart and checkout screens; we mirror the order and sync status back** — precisely what the code does today. The owner's "we add services to cart and check out using Woo/SureCart/FluentCart" meant *their* cart, not ours.

So `WCCheckoutProvider` is correct and must not be "fixed", and the order provider role stays as-is beyond 2a. **Order ownership and checkout ownership are separate questions**: 2a (the marketplace is the single order authority) shipped in 1.5.1 and remains right, because that is what stopped an unauthenticated webhook fatalling and what let buyers see their whole order history.

What the model actually requires is everything *after* payment: the marketplace owns the order, the processor reports status, and the trail (requirements → delivery → completion → payout) runs identically whichever processor took the money. That is 2b (done — already per-order) and 2d (one status-map layer).

Remove the corresponding `method.notFound` baseline entries as they become unreachable.

### Phase 5 — discrete fixes

**Seeder** (`MarketplaceSeeder::seed_withdrawals()`). Reproduced exactly on a clean run: `available_balance = -51.30`, `total_earned = 243.00`, vendor `wpss_vendor_aisha` — all matching the card.

The card's stated root cause is wrong: `afa9b47` (2026-07-25) already added both the `$available` cap and the COMPLETED-only ledger debit, and both are on `1.5.1`. The actual cause is that the cap uses **gross ledger credit and ignores the 14-day clearance window**:

```
gross credited        243.00   <- what the seeder caps against
seeder withdrew       145.80   = min(243*0.6, 243-10)
still in clearance    148.50
actually withdrawable  94.50   = 243.00 - 148.50
over-drawn             51.30   -> available_balance = -51.30
```

The card's own workaround figure ($94.50 available) *is* the clearance-adjusted cap. Fix: have `seed_wallet_ledger()` return clearance-aware available. Separately, the seeder never truncates, so repeat runs accumulate withdrawals against a freshly-recomputed gross balance — make it idempotent.

**MenuVisibility** (`src/Frontend/MenuVisibility.php:345`, `admin_menu` priority 999). `remove_submenu_page()` leaves `$title` null → `strip_tags(null)` deprecation on PHP 8.1+. Replace with CSS-hiding on the core `common` stylesheet; keep the `$submenu` entry so `get_admin_page_title()` and `user_can_access_admin_page()` resolve. Menu hiding stays cosmetic; access stays capability-gated.

**Delete `OrderMetabox`** (decision §2). Removes `DeliveryRepository::find_by_order()` and `ConversationRepository::get_messages()` undefined-method calls. Confirm `Admin::render_order_detail()` already surfaces deliveries and messages before deleting; if not, port them there.

**Repository `find_by_id()`** — `DisputeRepository.php:59` and `ExtensionRequestRepository.php:41` call `$this->find_by_id()`, which `AbstractRepository` does not define (`find()`, `find_by()`, `find_one_by()`). Latent — neither repo is instantiated. Fix to `find()` or delete.

**Pro `Service` model contract break** — `EDDProductProvider.php:78, 80, 84` writes `$price` and `$delivery_time` to `WPSellServices\Models\Service`, which declares neither and has no `#[\AllowDynamicProperties]`. Deprecated on PHP 8.2, **fatal on PHP 9**, and today the EDD price and delivery time are **silently discarded**.
